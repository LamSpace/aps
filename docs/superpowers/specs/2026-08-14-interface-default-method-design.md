# APS Phase 3: Interface Default Method Invocation — Design Spec

**Date:** 2026-08-14 **Status:** Design approved (simplified during implementation) **Phase:** 3 — Advanced Features

## 1. Motivation

For interface proxies, `AcceleratedProxy.invokeSuper(proxy, method, args)` currently
throws `AbstractMethodError` for every non-`Object` interface method — including
interface `default` methods that have a concrete implementation. A user interceptor
cannot fall through to the interface's default behavior; it must re-implement it
by hand.

This feature makes `invokeSuper` on a `default` interface method invoke that
method's default implementation, while keeping the existing `AbstractMethodError`
behavior for abstract (non-default) interface methods.

**Success criteria**

1. `invokeSuper` on a default method declared directly on the target interface
   returns the default implementation's result.
2. `invokeSuper` on a default method inherited from a parent interface returns the
   default implementation's result.
3. `invokeSuper` on a non-default interface method still throws
   `AbstractMethodError` (unchanged semantics).
4. Class-proxy super calls, `Object`-method dispatch, and existing interception
   behavior are unchanged.
5. Full unit tests, JMH benchmarks, and an updated benchmark report.

## 2. Design

### 2.1 Dispatch branch logic (core change)

The generated `dispatch(Method, Object[])` method currently routes interface-proxy
methods as follows (`DispatchGenerator.generateDispatch`): `Object` methods call
`INVOKESPECIAL java/lang/Object` directly, and all other interface methods throw
`AbstractMethodError`. This changes to a three-way split:

| Case                                       | Generated bytecode                                                     |
|--------------------------------------------|------------------------------------------------------------------------|
| `Object` method (`equals`/`hashCode`/`toString`) | `INVOKESPECIAL java/lang/Object` (unchanged)                            |
| `default` method (directly-declared **or** inherited) | `INVOKESPECIAL <target-interface>.<method>` with `itf = true` (fast path) |
| non-default interface method               | throw `AbstractMethodError` (unchanged)                                 |

The fast path emits a plain `INVOKESPECIAL` against the **target interface** — the
same zero-`MethodHandle`-overhead technique used for class-proxy super calls. This
works for both directly-declared and inherited defaults because of a JVM rule: the
interface **named in the symbolic reference** must be a direct superinterface of the
current class, and method resolution then walks the superinterface chain to find the
actual default implementation (whether declared on the target interface or a parent).

### 2.2 Files touched

| File | Change |
|------|--------|
| `generator/DispatchGenerator.java` | `generateDispatch` gains a parameter `String interfaceInternalName` (class proxies pass `null`); the interface branch emits `INVOKESPECIAL` for every `method.isDefault()` case. |
| `generator/InterfaceGenerator.java` | Pass the target interface's internal name into `generateDispatch`; `<clinit>` uses `getMethod` instead of `getDeclaredMethod` so inherited methods resolve. |
| `generator/ClassGenerator.java` | Pass `null` for the new parameter. |

No public API changes. `AcceleratedProxy.invokeSuper` and `DispatchTarget.dispatch`
signatures are unchanged. No new helper class is needed.

### 2.3 Design simplification during implementation

The original design used a `MethodHandles.Lookup.findSpecial` fallback (via a
`DefaultMethodInvoker` helper) for inherited default methods. Implementation testing
revealed this was unnecessary: a `findSpecial`/`INVOKESPECIAL` whose symbolic
reference names the **declaring** interface fails for inherited defaults
(`IncompatibleClassChangeError`: declaring interface is not a direct superinterface),
but naming the **target** interface succeeds and resolves the inherited default.
A single `INVOKESPECIAL` path therefore covers both cases, so the fallback and its
helper class were removed — simpler and faster.

## 3. Error handling

1. **Non-default interface method** → `AbstractMethodError` (unchanged; the existing
   `invokeSuperShouldThrowForInterfaceMethod` test continues to pass).
2. **Exception thrown inside the default method body** → propagated unchanged
   (the `INVOKESPECIAL` call propagates it directly, matching `invokeSuper`'s
   `throws Throwable`).

## 4. Testing

New `src/test/java/io/github/lamspace/DefaultMethodInvocationTest.java`. Every test
asserts that `invokeSuper` inside an interceptor returns the default implementation's
result.

| Scenario | Coverage |
|----------|----------|
| Directly-declared default — no-arg / with-args / primitive return / void / reference return | fast path across return types |
| Inherited default (`Child extends Parent`, default on `Parent`) | inherited resolution via the same fast path |
| Non-default interface method | still throws `AbstractMethodError` |
| Interceptor replaces default (no `invokeSuper`) | returns custom value |
| Default method throws | propagated unchanged |
| Argument modified before `invokeSuper` | default implementation sees the modified args |
| `Object` methods (`equals`/`hashCode`/`toString`) | still direct `Object` dispatch, no regression |

Existing tests that must keep passing: `shouldInterceptDefaultMethod`
(default methods are still intercepted), `invokeSuperShouldThrowForInterfaceMethod`
(non-default still throws).

## 6. Out of scope

- Multi-interface proxies and cross-interface default-method conflict resolution
  (Phase 3 item 2).
- Bridge methods and covariant-override edge cases for interface defaults.

## 7. Deliberate deviation from roadmap

The roadmap notes "需使用 `MethodHandles.Lookup.findSpecial()`". The final design
uses a direct `INVOKESPECIAL` against the target interface for **all** default
methods — no `findSpecial` at all — because it is both simpler and faster, and
consistent with the project's "eliminate `MethodHandle` overhead" goal.
