# APS Phase 3: Interface Default Method Invocation — Design Spec

**Date:** 2026-08-14 **Status:** Design approved **Phase:** 3 — Advanced Features

## 1. Motivation

For interface proxies, `AcceleratedProxy.invokeSuper(proxy, method, args)` currently
throws `AbstractMethodError` for every non-`Object` interface method — including
interface `default` methods that have a concrete implementation. A user interceptor
cannot fall through to the interface's default behavior; it must re-implement it
by hand.

This feature makes `invokeSuper` on a `default` interface method invoke that
method's default implementation, while keeping the existing `AbstractMethodError`
behavior for abstract (non-default) interface methods.

**Success criteria**

1. `invokeSuper` on a default method declared directly on the target interface
   returns the default implementation's result.
2. `invokeSuper` on a default method inherited from a parent interface returns the
   default implementation's result.
3. `invokeSuper` on a non-default interface method still throws
   `AbstractMethodError` (unchanged semantics).
4. Class-proxy super calls, `Object`-method dispatch, and existing interception
   behavior are unchanged.
5. Full unit tests, JMH benchmarks, and an updated benchmark report.

## 2. Design

### 2.1 Dispatch branch logic (core change)

The generated `dispatch(Method, Object[])` method currently routes interface-proxy
methods as follows (`DispatchGenerator.generateDispatch`): `Object` methods call
`INVOKESPECIAL java/lang/Object` directly, and all other interface methods throw
`AbstractMethodError`. This changes to a four-way split:

| Case                                                        | Generated bytecode                                                    |
|-------------------------------------------------------------|-----------------------------------------------------------------------|
| `Object` method (`equals`/`hashCode`/`toString`)            | `INVOKESPECIAL java/lang/Object` (unchanged)                           |
| default method, declared **directly** on the target interface | `INVOKESPECIAL <target-interface>.<method>` with `itf = true` (fast path) |
| default method, **inherited** from a parent interface       | `INVOKESTATIC DefaultMethodInvoker.invokeDefault(this, method, args)`  |
| non-default interface method                                | throw `AbstractMethodError` (unchanged)                                |

The fast path emits a plain `INVOKESPECIAL` — the same zero-`MethodHandle`-overhead
technique already used for class-proxy super calls. It is legal because the
generated class directly `implements` the target interface, and the JVM permits
`INVOKESPECIAL` on an interface default method only when that interface is a
*direct superinterface* of the current class.

Inherited default methods (whose `getDeclaringClass()` is a parent interface, not
the directly-implemented one) do **not** satisfy the direct-superinterface rule, so
they fall back to `MethodHandles.Lookup.findSpecial` (Section 2.3).

No public API changes. `AcceleratedProxy.invokeSuper` and `DispatchTarget.dispatch`
signatures are unchanged.

### 2.3 Inherited-default fallback (`DefaultMethodInvoker`)

Plain Java helper (no bytecode generation), so it is directly unit-testable:

```java
public final class DefaultMethodInvoker {
    private static final Map<Method, MethodHandle> CACHE =
            new ConcurrentHashMap<>();

    public static Object invokeDefault(Object proxy, Method method,
                                       Object[] args) throws Throwable {
        MethodHandle mh = CACHE.computeIfAbsent(method,
                m -> resolve(m, proxy.getClass()));
        return mh.bindTo(proxy).invokeWithArguments(args);
    }

    private static MethodHandle resolve(Method method, Class<?> proxyClass) {
        try {
            MethodType type = MethodType.methodType(
                    method.getReturnType(), method.getParameterTypes());
            return MethodHandles.lookup().findSpecial(
                    method.getDeclaringClass(), method.getName(),
                    type, proxyClass);
        } catch (NoSuchMethodException | IllegalAccessException e) {
            throw new IllegalStateException(
                    "Cannot bind default method: " + method, e);
        }
    }
}
```

- **specialCaller = `proxy.getClass()`**: the generated class implements the target
  interface, so it is also a subtype of any parent interface, satisfying
  `findSpecial`'s requirement that the special caller be a subtype of the interface
  for interface methods.
- The resulting `MethodHandle` is early-bound to the interface method and receiver-
  agnostic, so caching by `Method` key is safe — the first resolution's
  `specialCaller` does not affect subsequent reuse.
- `invokeWithArguments` boxes/unboxes automatically, matching the `Object[]` shape
  that `dispatch` already produces.

## 3. Error handling

1. **Non-default interface method** → `AbstractMethodError` (unchanged; the existing
   `invokeSuperShouldThrowForInterfaceMethod` test continues to pass).
2. **Inherited-default `findSpecial` failure** (only possible if the method is not a
   public default method or the caller is not a subtype — an unexpected state) →
   `IllegalStateException` with the `Method` in the message and the original
   exception as cause.
3. **Exception thrown inside the default method body** → propagated unchanged
   (`invokeDefault` declares `throws Throwable`, matching `invokeSuper`).

## 4. Testing

New `src/test/java/io/github/lamspace/DefaultMethodInvocationTest.java` (or extend
`AcceleratedProxyInterfaceProxyTest`). Every test asserts that
`invokeSuper` inside an interceptor returns the default implementation's result.

| Scenario | Coverage |
|----------|----------|
| Directly-declared default — no-arg / with-args / primitive return / void / reference return | fast path across return types |
| Inherited default (`Child extends Parent`, default on `Parent`) | `findSpecial` fallback |
| Non-default interface method | still throws `AbstractMethodError` |
| Interceptor replaces default (no `invokeSuper`) | returns custom value |
| Default method throws | propagated unchanged |
| Argument modified before `invokeSuper` | default implementation sees the modified args |
| `Object` methods (`equals`/`hashCode`/`toString`) | still direct `Object` dispatch, no regression |

Existing tests that must keep passing: `shouldInterceptDefaultMethod`
(default methods are still intercepted), `invokeSuperShouldThrowForInterfaceMethod`
(non-default still throws).

## 6. Out of scope

- Multi-interface proxies and cross-interface default-method conflict resolution
  (Phase 3 item 2).
- Bridge methods and covariant-override edge cases for interface default methods —
  not addressed unless tests reveal a concrete failure.
- Changing the `AbstractMethodError` behavior for non-default interface methods.

## 7. Deliberate deviation from roadmap

The roadmap notes "需使用 `MethodHandles.Lookup.findSpecial()`". This design keeps
`findSpecial` only for *inherited* default methods; for directly-declared defaults it
uses a direct `INVOKESPECIAL`, which is faster and consistent with the project's
"eliminate `MethodHandle` overhead" goal. This was chosen explicitly for the
best-performing implementation.
