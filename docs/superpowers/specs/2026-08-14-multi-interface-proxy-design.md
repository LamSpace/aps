# APS Phase 3: Multi-Interface Proxy — Design Spec

**Date:** 2026-08-14 **Status:** Design approved **Phase:** 3 — Advanced Features

## 1. Motivation

`AcceleratedProxy.proxy()` currently accepts a single target — a class or a single interface. `InterfaceGenerator` generates a class that implements exactly one interface plus `DispatchTarget`. A user cannot create a single proxy object that is simultaneously usable through several interfaces (e.g. both `Greeter` and
`Auditable`), a capability that `java.lang.reflect.Proxy.newProxyInstance` provides via its `Class<?>[]` parameter.

This feature lets one generated proxy class implement multiple interfaces, so a single object can be cast to any of them while sharing one interception pipeline. The single-interface proxy becomes the `N == 1` special case of this feature.

**Success criteria**

1. `proxy(Class<?>[] interfaces, ...)` generates one class implementing all given interfaces; the returned object can be cast to each interface.
2. Single-interface proxies are unchanged in behavior and in generated bytecode (the `N == 1` case), so existing tests and JMH numbers are unaffected.
3. Methods with the same signature and return type across interfaces are merged into a single implementation (no duplicate bytecode).
4. Genuinely ambiguous cases are rejected at `proxy()` time with a clear
   `IllegalArgumentException` (see §3.3).
5. `invokeSuper` on a merged `default` method resolves the correct default implementation; on an abstract merged method it still throws
   `AbstractMethodError`.
6. Full unit tests, an updated roadmap, and updated README documentation.

## 2. Design

### 2.1 Public API

Two new overloads, returning `Object` (the caller casts). Existing single-interface overloads keep their signatures and `T` return type unchanged.

```java
Object proxy(Class<?>[] interfaces, Interceptor interceptor);

Object proxy(Class<?>[] interfaces, Group... groups);
```

There is no constructor-argument overload for interfaces: interfaces have no super constructor, and the existing interface path already ignores `constructorArgs`.

### 2.2 Internal unification: interface path → `Class<?>[]`

The interface path is unified internally so that single-interface is the `N == 1`
case. The class path (`ClassGenerator`) is deliberately left untouched — class proxying differs semantically (`extends` vs `implements`, `LookupManager` vs
`MethodHandles.lookup()`, super constructor args, `INVOKESPECIAL super`), and multi-interface only ever applies to interfaces.

| Component                             | Change                                                                                                                                                                                  |
|---------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `matchMethods`                        | Parameter becomes `Class<?>[]`; merges each interface's `getMethods()`, dedups by signature, performs conflict detection (§3.3), then stable-sorts and runs the existing `Group` chain. |
| `InterfaceGenerator`                  | Constructor takes `Class<?>[]`; `implements` = all interfaces + `DispatchTarget`; iterates the merged method list instead of a single `interfaceClass.getMethods()`.                    |
| `InterfaceDispatcher.dispatchMethods` | Accepts the merged method list; per-method code generation unchanged.                                                                                                                   |
| `generateProxyClass`                  | Routes the interface branch through the array version.                                                                                                                                  |
| Generated class name                  | `N == 1` keeps the current `SimpleName$$AcceleratedProxy$$<n>` (byte-identical); `N > 1` uses `MultiInterface$$AcceleratedProxy$$<n>`.                                                  |
| Proxy class cache                     | Cache key extended to include the interface array (array-based `equals`/`hashCode`); single-interface keeps its existing cache semantics.                                               |

`N == 1` byte-identity is the load-bearing invariant for the "zero benchmark impact" claim (§6): for a single interface the merged method set, sort order, and emitted class must be identical to today's output.

### 2.3 Method merging & conflict resolution

Merging key = method signature (name + parameter types). Resolution rules:

| Scenario                                                                     | Resolution                                                |
|------------------------------------------------------------------------------|-----------------------------------------------------------|
| Same signature + same return type                                            | Merge into one implementation.                            |
| Same signature + same return type, both abstract                             | Merge; `invokeSuper` throws `AbstractMethodError`.        |
| Same signature + same return type, one `default` + one abstract              | Merge; `invokeSuper` calls the `default` implementation.  |
| Same signature + same return type, both `default` (from distinct interfaces) | **Throw `IllegalArgumentException`** — genuine ambiguity. |
| Same signature + different return types (including covariant)                | **Throw `IllegalArgumentException`**.                     |

Two deliberate simplifications (see §7):

- **No covariant return-type support.** Any differing return type is rejected outright rather than resolving the most-specific type (which would force the generated method to use the subtype as its return descriptor plus a `CHECKCAST`).
- **No "most-specific-interface-wins" for default methods.** Two `default`s from distinct interfaces always throw; callers pass only the more specific interface.

`Object` methods (`equals`/`hashCode`/`toString`) are **not** part of an interface's `getMethods()` — they are inherited directly by the generated class and never participate in merging. A parent/child pair (`{A, B}` where `A extends B`) is handled by signature dedup — `B`'s methods are already in `A.getMethods()`.

### 2.4 Dispatch & `invokeSuper` correctness

A merged method is one JVM method with one generated implementation, but it may be reached through the `Method` object of either interface. `Method.hashCode()` includes the declaring class, so `A.foo()` and `B.foo()` have different hashes. The
`dispatch(Method, Object[])` switch must therefore route **both** hashes to the same handler:

- merged with a `default` source → `INVOKESPECIAL` against that default's declaring interface (reusing the Phase-3 default-method fast path);
- merged and abstract → throw `AbstractMethodError`.

`intercept(proxy, method, args)` receives the canonical (first-declared interface's)
`Method` object. Both-`default` and differing-return cases never reach code generation (rejected in `matchMethods`).

### 2.5 Files touched

| File                                 | Change                                                                                                 |
|--------------------------------------|--------------------------------------------------------------------------------------------------------|
| `AcceleratedProxy.java`              | New `Class<?>[]` overloads; `matchMethods`/`generateProxyClass`/cache key extended for the array form. |
| `generator/InterfaceGenerator.java`  | `Class<?>[]` constructor; multi-interface `implements` list and class name.                            |
| `generator/InterfaceDispatcher.java` | Accept merged method list.                                                                             |
| `generator/DispatchGenerator.java`   | Route multiple `Method` hashes to one handler for merged methods.                                      |

No change to `ClassGenerator`, `Interceptor`, `Group`, `DispatchTarget`, or the public `invokeSuper` signature.

## 3. Error handling

1. **Two `default` methods with the same signature** → `IllegalArgumentException`
   at `proxy()` time, naming the method and the two interfaces.
2. **Same signature, different return types** → `IllegalArgumentException` at
   `proxy()` time, naming the method, the two interfaces, and the two return types.
3. **`null` array / empty array / array containing a non-interface `Class`** →
   `IllegalArgumentException`.
4. **Merged abstract method via `invokeSuper`** → `AbstractMethodError` (unchanged).
5. Exceptions thrown inside a `default` implementation propagate unchanged.

## 5. Benchmark

**Conclusion: no impact on existing numbers.** JMH measures invocation only (`@Setup` creates the proxy once; `@Benchmark` methods call it). Merging, dedup, and conflict detection all run at creation time, outside the measured loop, and the generated per-method hot path (GETFIELD interceptor → GETSTATIC Method → box args →
`INVOKEINTERFACE intercept` → unbox) is independent of interface count. The `N == 1`
case is byte-identical, and the class-proxy path is untouched.

The guard is procedural, not theoretical: run the existing JMH suite before and after, and require the interface- and class-proxy numbers to be unchanged.

Optional (not required): a new "multi-interface vs. equivalent single-interface"
pair that turns "interface count adds no per-call cost" into a measured fact.

## 7. Deliberate decisions

1. **No covariant return-type resolution** — differing return types are always rejected. Rare in practice; supporting it would force subtype return descriptors and extra `CHECKCAST` for little value.
2. **No most-specific-interface-wins for default conflicts** — two `default`s from distinct interfaces always throw. Callers pass the more specific interface.
3. **Internal unification, stable public API** — the interface path is unified to
   `Class<?>[]` internally, while the public single-interface overloads (returning
   `T`) are preserved as thin delegates; the multi-interface overloads return
   `Object`. The class path is not merged into the array pipeline.

## 8. Out of scope

- Class + interface proxying (`extends` a class while also `implements` interfaces).
- Covariant return-type merging (see §7.1).
- Most-specific-interface default resolution (see §7.2).
