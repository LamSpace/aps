## Root Cause Analysis (v1.0 → v1.1 fix)

APS v1.0 generated bytecode that called `MethodHandle.bindTo(this).asSpreader(Object[].class, n)` on
**every method invocation**, creating two new MethodHandle instances (BoundMethodHandle + SpreaderHandle)
per call. This added ~200–300ns of allocation overhead.

**v1.1 fix:** `asSpreader` is now applied once in `<clinit>` — the static `_handle$X` field stores a
pre-spread handle. The generated override only calls `bindTo(this)`, eliminating the per-call
SpreaderHandle allocation.

Remaining overhead vs CGLib comes from:
- `bindTo(this)` per call (BoundMethodHandle allocation, ~10–20ns)
- `Object[]` packing and argument boxing per call (~5–15ns)
- `MethodHandle.invoke` vs direct `invokespecial` (~10–30ns)

These are inherent to the MethodHandle-based design. Eliminating them would require switching to
direct `invokespecial` bytecode generation (like CGLib), at the cost of losing the MethodHandle
super-call API exposed to callbacks.
