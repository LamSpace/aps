**Key finding:** APS interface proxy achieves performance parity with JDK's native
`java.lang.reflect.Proxy` across all scenarios, while using MethodHandle-based dispatch
instead of reflection. The 1ns-level differences are within measurement noise.

## Class Proxy Root Cause (v1.0 → v1.1 fix)

APS v1.0's class proxy generated bytecode that called `MethodHandle.bindTo(this).asSpreader(Object[].class, n)`
on **every method invocation**, creating two new MethodHandle instances per call (~200-300ns overhead).

**v1.1 fix:** `asSpreader` is applied once in `<clinit>` — the static `_handle$X` field stores a pre-spread handle.
The generated override only calls `bindTo(this)`, eliminating the per-call SpreaderHandle allocation.

Remaining class-proxy overhead vs CGLib:
- `bindTo(this)` per call (BoundMethodHandle allocation, ~10-20ns)
- `Object[]` packing and argument boxing per call (~5-15ns)
- `MethodHandle.invoke` vs direct `invokespecial` (~10-30ns)

Interface proxies avoid all three: no `bindTo` (no superHandle needed), minimal `Object[]` allocation
that the JIT can scalar-replace, and the `InterfaceCallback.intercept` call is equivalent in cost
to `InvocationHandler.invoke`.
